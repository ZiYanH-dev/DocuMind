# 检索链路（多路召回 + 融合 + 重排）

> 代码：`backend/app/retrieval/`，入口 `pipeline.retrieve()`。
> 被 `app/agent/tools.py` 的 `search_knowledge` 调用，由 Agent 自主触发。

## 1. 它是什么

检索是一段四步流水线，把一个问题变成按相关度降序的片段列表。
每一步失败都降级而不是中断，最终一定返回一个列表，可能为空。

```
rewrite_queries()  →  [_vector_recall() ×N]  →  rrf_fuse()  →  rerank()  →  top_k
                   →  [_keyword_recall() ×N]  ↗
```

单次检索的完整步骤：

1. 查询改写，得到原问题加若干变体。
2. 每条查询分别走向量召回，关键词开关打开时再走一遍关键词召回。
3. 所有路的结果做倒数排名融合。
4. 对融合候选调重排接口，取最终 `top_k`。

## 2. 四段的实现

| 段 | 文件 | 做法 | 关键参数 |
| --- | --- | --- | --- |
| 查询改写 | `rewrite.py` | 提示词让 LLM 输出 JSON 字符串数组，剥掉代码块围栏后解析 | `rewrite_count=2` |
| 向量召回 | `pipeline._vector_recall` | `embed_query()` 后走 pgvector 余弦距离，SQL 层按阈值过滤 | `vector_recall_k=10`、`score_threshold=0.3` |
| 关键词召回 | `keyword.py` | jieba 分词后建 BM25 索引，按分数降序取前若干条，分数为 0 的不召回 | `keyword_recall_k=10` |
| 融合 | `fusion.py` | 倒数排名融合，只看名次不看分数 | `fusion_k=60` |
| 重排 | `rerank.py` | 调百炼原生重排接口，按「问题与片段」打分重排 | `rerank_model=gte-rerank-v2`、`rerank_top_n=4` |

召回条数都是片段级，与最终 `top_k` 是两个概念：先各路多召回，再由融合与重排收敛到 `top_k`。

## 3. 融合为什么用 RRF

向量路给的是余弦相似度，取值范围 0 到 1。
关键词路给的是 BM25 分数，上界随语料规模浮动，可能是 0 到几十。
两路分数尺度不同，直接相加会让 BM25 分数压过向量分。

RRF 只用名次：第 `rank` 名贡献 `1 / (k + rank)` 分，同一片段在多路出现则分数累加。
因此被两路同时召回的片段自然排到前面。

返回结果里三个分数字段：

| 字段 | 含义 |
| --- | --- |
| `score` | 归一化到 0 到 1 的融合分，重排后替换为重排分 |
| `rrf_score` | 原始融合分 |
| `recall` | 该片段被哪几路召回，值为 `vector`、`keyword` 或重排后追加 `+rerank` |

## 4. 开关与退化链

每一路都可在 `config/app.yaml` 的 `retrieval` 段关闭。

| 关掉的项 | 退化后的链路 |
| --- | --- |
| `rewrite_enabled` | 只用原问题召回 |
| `keyword_enabled` | 只走向量召回 |
| `rerank_enabled` | 直接取融合结果前 `top_k` 条 |
| 关键词与重排都关 | 退化为纯向量检索 |
| 只关重排 | 退化为混合召回 |

因此「纯向量 RAG」不是另一套代码，而是把开关全关掉的同一条链路。
评测脚本用它做对照实验。

## 5. 缓存

检索结果按用户与问题文本缓存 300 秒，key 为 `documind:retrieval:{user_id}:{sha1(问题)}`。
问题文本取 sha1 摘要，避免长问题把 key 拉长。

文档增删时 `DocumentService._invalidate_user` 按前缀清空该用户的检索缓存。
评测脚本可传 `use_cache=False` 测真实耗时与效果。

## 6. 边界与注意事项

| 项 | 说明 |
| --- | --- |
| 改写失败 | 捕获全部异常返回空列表，调用方退回单查询检索，不中断问答 |
| 改写去重 | 与原始问题完全相同的变体被剔除，避免同一查询重复计入 RRF |
| 重排失败 | `httpx` 请求异常或返回体无 `results` 时原样返回融合顺序，不影响主链路 |
| 重排超时 | 20 秒，超时即放弃重排 |
| 重排候选上限 | 最多送 30 条进重排，控制 token 消耗，超出部分靠融合分排序 |
| 重排接口不在 OpenAI 协议内 | 百炼重排路径需单独拼 `RERANK_PATH`，复用 LLM 的 Key，不引入新依赖 |
| BM25 索引在进程内 | 多 worker 部署时每个进程各有一份索引，失效需在各进程内生效 |
| 空语料 | 语料指纹为 `empty` 时跳过关键词这一路，不建索引 |

## 7. 与回答的关系

检索只负责给片段，不负责生成。
Agent 拿到的是已经格式化成 `[来源: 标题, 相关度: 0.82]` 加正文的文本。
引用来源另由 `SourceInfo` 收集器按结构输出，不走文本解析。
